## Architecture Decisions

- This project's `shadcn` CLI (v4.19.0) generates components on `@base-ui/react` primitives with the `base-nova` style, not the classic Radix-based `new-york`/`default` style from most shadcn documentation and training data. Generated files use `data-slot`, `data-open`/`data-closed`, and a `render` prop (not `asChild`) for composition. Future `shadcn add` calls will follow this same convention automatically — do not hand-write Radix-based patterns.
- shadcn's semantic color tokens (`background`, `foreground`, `card`, `popover`, `primary`, `secondary`, `muted`, `destructive`, `border`, `input`, `ring`) are defined in `app/globals.css` as aliases onto the brand tokens in `context/ui-context.md` (`--bg-base`, `--text-primary`, `--accent-primary`, etc.), so unmodified `components/ui/*` files render in the correct dark theme. App-level code should keep using the brand utility names (`bg-base`, `text-copy-primary`, `border-surface-border`, `text-brand`, `bg-accent-dim`, `bg-ai`, `text-ai-text`, `bg-state-error`, etc.) rather than the shadcn semantic names, to stay aligned with `ui-context.md`.
- Theme is forced dark via a `dark` class on `<html>` in `app/layout.tsx` (no toggle, no light variant) since the product has no light mode.
- `EditorNavbar` and `ProjectSidebar` (`context/feature-specs/02-editor-chrome.md`) are stateless/controlled: they take `isSidebarOpen`/`isOpen` plus callback props rather than owning state themselves, since the spec describes reusable chrome shells, not a page. `ProjectSidebar` is `fixed`, positioned `top-14` (below the navbar) so it floats as an overlay without pushing canvas content, per the "floating sidebar overlay" layout pattern in `ui-context.md`. `components/editor/editor-shell.tsx` is the component that owns the toggle state and composes the two — kept separate from `EditorNavbar`/`ProjectSidebar` so those stay easy to test and reuse independently of how their state is managed.
- `components/editor/editor-dialog.tsx` implements the "Dialog Pattern" from the spec as styled wrappers (`EditorDialogContent`, `EditorDialogFooter`) around the unmodified `components/ui/dialog.tsx` primitives, rather than a new dialog component — this keeps `components/ui/*` untouched per the protected-foundation-components rule while giving future features brand-token styling (`rounded-3xl`, `bg-surface`) to compose actual dialogs from.
- Auth uses `proxy.ts`, not `middleware.ts` — this Next.js version (16) renamed the convention (same `NextMiddleware` contract, file/export name only), per `node_modules/next/dist/docs/01-app/01-getting-started/16-proxy.md`. `@clerk/nextjs` (v7.8.2) already ships proxy-aware exports for this.
- Route protection is centralized in `proxy.ts` via `clerkMiddleware` + `createRouteMatcher` (allowlist the sign-in/sign-up routes, `auth.protect()` everything else) rather than per-page `auth()` checks, per the explicit `03-auth.md` spec ("Protect everything else by default", checklist requires `proxy.ts` to exist and cover all routes). Note: the installed `@clerk/nextjs` deprecates `createRouteMatcher` in favor of resource-based (per-page) auth checks — it still works and is not removed in this version, so it was kept to match the spec; revisit if it's removed in a future `@clerk/nextjs` upgrade (migration guide: https://clerk.com/docs/guides/development/upgrading/upgrade-guides/migrate-from-create-route-matcher).
- Clerk appearance is configured once, globally, in `app/layout.tsx`'s `ClerkProvider` (`theme: dark` from `@clerk/ui/themes` + `variables` mapped to the app's CSS custom properties) rather than per-component — every Clerk component (`SignIn`, `SignUp`, `UserButton`, etc.) inherits it automatically, so no separate appearance config was added for `UserButton` in the navbar.

- **Bug fix, Feature 01 design system** (found while building Feature 04, fixed in `app/globals.css`): the brand token `--color-base: var(--bg-base)` in the `@theme inline` block was registered under Tailwind's `--color-*` namespace, which auto-generates `text-*`/`border-*`/`ring-*`/etc. utilities for every color key — not just `bg-*`. Because the key was literally named `base`, this collided with Tailwind's own built-in `text-base` font-size scale keyword, and the color utility won the cascade: any element sized with the plain `text-base` class (no other explicit color class) silently got `color: var(--bg-base)` — near-black text on a near-black background. This was invisible in every dialog title (`DialogTitle` in `components/ui/dialog.tsx` uses `text-base` for sizing) and in every `Input`/`Textarea` value (both use `text-base`), reported by the user as "typed text doesn't show" in the Create Project dialog, and also affected `CardTitle`. Root-caused (not patched per-component, since `components/ui/*` is protected foundation code and the defect wasn't in those files) by removing `--color-base` from the theme block and re-declaring `bg-base` as a plain `@utility bg-base { background-color: var(--bg-base); }` outside the color namespace — Tailwind no longer thinks `base` is a color name, so `text-base` reverts to its built-in font-size meaning, while `bg-base` keeps working exactly as before (verified: computed `background-color` on `.bg-base` unchanged, computed `color` on `DialogTitle`/`Input` now resolves to `--text-primary` as intended). No other brand token name collides with a Tailwind scale keyword (checked: surface, elevated, subtle, copy-primary, copy-secondary, copy-muted, copy-faint, brand, accent-dim, ai, ai-text, state-error, state-success, state-warning — none match Tailwind's built-in size/color keyword lists). Take-away for future tokens: avoid naming a brand color the same as a Tailwind core scale keyword (`xs`/`sm`/`base`/`lg`/`xl`/`2xl`.../`DEFAULT`), since `--color-*` collisions like this fail silently (no build error, no lint error — only visibly wrong computed color) and are easy to miss in a quick visual check at normal screenshot scale (had to zoom in to actually notice the low-contrast text).
